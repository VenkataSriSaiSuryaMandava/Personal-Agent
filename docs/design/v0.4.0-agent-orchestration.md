## 2. Agent operating model

Use a central orchestrator and eight specialist capabilities:

1. Discovery: retrieve permitted job listings.
2. Matching: evaluate personalized compatibility.
3. Research: collect and summarize sourced public information.
4. Documents: prepare evidence-based application materials.
5. Networking: discover relevant professional contacts.
6. Communication: prepare and execute authorized messages.
7. Interview: prepare questions and interview-related records.
8. Workflow: coordinate scheduling, recovery and follow-ups.

Agents are typed modules, not independent unrestricted LLMs.

All operations must have:
- Registered capability identifier and version.
- Validated input and output contracts.
- Explicit runtime and data permissions.
- Resource and time limits.
- Defined failure and cancellation behavior.
- Structured audit events.
- Owner or isolated Guest storage context.

The model cannot create new capabilities, grant permissions,
select arbitrary endpoints or execute shell commands.

Support Manual, Assisted and Proactive operating modes.

Proactive is the preferred default after Owner configuration.
No scheduling or external access begins before applicable
sources, permissions and operating limits are configured.

Guest workflows remain bounded and on demand.

## 3. Workflow engine

Proposed backend modules:

aegis/schemas/workflows.py
aegis/services/agents/
aegis/services/workflows/
aegis/storage/workflows.py
aegis/api/workflows.py

Initial schema additions in Batch 4.4B:

workflow_runs:
- id, user_id, workflow_type, definition_version
- status, revision, request_key
- created_at, updated_at, cancellation_requested

workflow_steps:
- id, user_id, run_id, step_key, capability
- status, validated input and output references
- attempt_count, available_at
- lease_token, lease_expires_at
- safe error code, revision

workflow_events:
- monotonic event identifier
- user_id, run_id, optional step_id
- event_type, created_at, safe metadata

Use owner-qualified foreign keys and unique step identities.
Deduplicate requests within the owner and workflow scope.
Reject conflicting reuse of a request key.

Persist only bounded, validated data.
Prefer references to existing records over duplicated content.

Workflow states:
- queued
- running
- waiting_approval
- executing
- completed
- failed
- cancelled
- uncertain

State transitions must be explicitly validated.

Use BEGIN IMMEDIATE to claim eligible work atomically.
Do not hold database transactions during network operations.

Lease ownership must be checked before committing results.
Expired leases must not allow stale workers to overwrite results.

Recover interrupted read-only or idempotent operations.
Never blindly replay an external action with an uncertain result.

Cancellation prevents further dispatch.
Do not claim that cancellation reverses external execution.

Add workflow schedules in Batch 4.7.
Schedules are Owner-only and run only while the private
runtime is available.

No scheduled work may inherit a Guest request database.
Never store browser sessions or bearer tokens as worker credentials.

## 7. Discovery persistence

Schema 8 restricts providers through database CHECK
constraints, Python schemas and frontend types.

Batch 4.4C must update all affected contracts together.

Preserve:
- Existing source and listing identifiers.
- Application links.
- Owner-qualified foreign keys.
- Existing application status records.
- Existing cached listings.

If table reconstruction is necessary, preserve data,
indexes, triggers and constraints through a tested migration.

Use versioned normalized listing metadata.
Include employer identity, requisition ID where available,
canonical URL, source provenance and freshness.

Deduplicate exact identities and supported canonical links.
Do not merge unrelated jobs based only on similar titles.

Prefer authoritative employer listings while retaining
alternate source provenance.

A partial, paginated or filtered result is not evidence
that absent jobs have closed.

Preserve existing snapshots on failed refreshes.
Only close absent listings after verified complete snapshots.

Current limits remain in force until measured changes
are approved:
- 100 configured sources.
- 1000 listings per source.
- 64 MiB logical cache.
- 8 MiB maximum response.
- Three concurrent source requests.
- 15-second request timeout.
- Six-hour cache freshness target.

Large employers may require permitted filtered or
paginated discovery rather than full-board downloads.

Do not claim comprehensive job-market coverage.

## 8. Personalized recommendations

- Required and preferred qualifications.
- Target roles and experience evidence.
- Location and work arrangements.
- Employment preferences.
- Explicit compensation and industry preferences.
- Owner feedback and saved opportunities.

Unknown evidence is not a negative qualification.

Persist recommendation versions and profile revisions.
Invalidate stale scores when relevant evidence changes.

Support save, dismiss and preference feedback.
Do not silently rewrite Owner preferences.

representative fixtures before replacing default ranking.

## 11. AI integration and privacy

The authorized Gemini provider remains unchanged.

Current cloud policy permits reviewed public or
synthetic content only.

Do not send private resumes, email contents, credentials,
personal profile data or private conversational context
to Gemini under the existing policy.

Use local operations for private matching, document
assembly and communication preparation.

Structured output and function calling are candidate
extensions, subject to configured-model verification.

Model output is untrusted.
Validate every operation against registered schemas.

Route all model requests through the existing outbound
gateway, content review and rate limits.

Never invoke a provider directly to bypass those controls.

No automatic cloud transmission of private information
or unreviewed web content.

External pages and messages are data, not instructions.

Broader private AI processing requires separate
explicit security approval.

## 12. OAuth and credential security

Batch 4.5 introduces Owner-only connected accounts.

Use official delegated OAuth authorization.

Implement state validation, PKCE where supported,
exact redirect URIs and session-bound authorization.

Validate account identity, granted scopes and expiration.

Request minimum necessary scopes.
Separate send authorization from inbox access.

Use authenticated token encryption with a separate
runtime key and documented key lifecycle.

Never put tokens or encryption keys in Git, frontend
state, ordinary logs or AI prompts.

Define safe token refresh, revocation and disconnection.

Keep private backups and credential recovery consistent.

No connected-account credentials in Guest runtime.

Provider registration, verification and permitted scopes
must be confirmed before claiming integration availability.

## 13. External execution approvals

Existing manual approval records remain non-executable.

Introduce enforceable execution approvals binding:
- Owner and authenticated approval session.
- Connected account and granted capability.
- Exact action and recipient.
- Exact subject, body and attachment digests.
- Creation and expiration timestamps.
- Single-use execution state.

Proposed approval lifetime: ten minutes.

Editing any bound payload invalidates the approval.

Claim approval atomically before dispatch.
Recheck account, permissions, payload, emergency stop,
session validity and expiration.

Prevent concurrent duplicate sends.

After an ambiguous network result, record uncertain
execution and require reconciliation.

Do not equate provider acceptance with delivery.

No automatic external messages, job submissions
or consequential actions without explicit approval.
